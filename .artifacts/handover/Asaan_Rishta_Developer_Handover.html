Asaan Rishta Developer Handover Requirements

Repository-based current-state specification
Prepared for Flutter developers, backend owners, QA, and product owners
Source snapshot reviewed 30 September 2026

This document maps the implemented client and supporting Firebase code. It is a handover baseline, not a claim that every flow works in production. A statement marked Verified in code identifies an implementation path. Backend outcomes, live payment settlement, and platform behavior need separate confirmation. Open questions are kept apart from implementation facts.

1. Executive overview and evidence rules

Asaan Rishta is a Flutter matrimonial application with public browsing, ordinary user and matrimonial account paths, profile discovery, vendors, chat, connects, payments, and account tools. The client uses GetX for routes and controllers, HTTP repositories for a separate backend, and Firebase for authentication support, chat, messaging, storage, notifications, and functions. Local state includes secure storage, SharedPreferences, and Hive message cache. Sources: lib/main.dart:45-140; lib/app/core/routes/app_pages.dart; lib/app/core/services/dependency_injection.dart; pubspec.yaml.

Evidence labels. A = Verified current client behavior in named code; B = documented intention with no independent implementation confirmation; C = proposed behavior or unresolved question. All module descriptions below are A unless explicitly marked B or C. A cited call establishes that the client attempts an operation, not that the remote system accepts it.

2. Repository and architecture

Inventory. The repository contains the Flutter application under lib; assets; Android and iOS projects; Dart unit, widget, and integration tests; JavaScript Firebase callable functions under functions; Fastlane files; environment examples; and several issue-specific Markdown notes. Routes and bindings live under lib/app/core. UI is under lib/app/views, controllers under lib/app/viewmodels and some view folders, domain use cases and repositories under lib/app/domain, and chat storage under lib/app/data and core services. Sources: lib/app/core/routes/app_pages.dart; lib/app/core/services/dependency_injection.dart; functions/index.js; test/; integration_test/.

Startup. Main loads .env, initializes secure storage and Hive, initializes Firebase and App Check, registers repositories/use cases, installs a Firebase background message handler, initializes deep links and screen security, and chooses onboarding or splash from stored onboarding state. Initialization errors for environment, secure storage, and Hive are logged but startup continues. Splash waits for AuthService and routes signed-in users to bottom navigation or partner preferences, with role 3 bypassing preferences; guests go to account type. Sources: lib/main.dart:45-140; lib/app/views/splash/splash_controller.dart:24-112.

Technology. Dart SDK constraint ^3.12.1; GetX, dartz, HTTP and Dio, Firebase Core/Auth/Firestore/Storage/Messaging/App Check/Functions/Remote Config, SharedPreferences, flutter_secure_storage, Hive, in_app_purchase, WebView, media and notification plugins. Package declarations establish dependencies, not proof every integration is active. Source: pubspec.yaml:53-174.

Data ownership. The backend API supplies registration, profile/catalogue data, favorites, connects, transactions, vendors, and contact operations. Firestore stores chat users, conversations, presence, preferences flags, and notification data. Hive caches messages; secure storage and SharedPreferences hold account/session values. The client combines data from these systems; no shared cross-system transaction is visible. Sources: lib/app/domain/repository/user_management_repo/user_management_repo_impl.dart; lib/app/domain/repository/system_config_repo/system_config_repo_impl.dart; lib/app/core/services/firebase_service/firebase_service.dart; lib/app/core/services/hive_message_service.dart; lib/app/core/services/secure_storage_service.dart.

4. Module requirements and acceptance criteria

M01 Onboarding, account choice and guest browsing

Entry and actions. Onboarding is selected at first run; account choice offers Rishta User, Matrimonial, login, guest, user guide, and contact. Selected account type is saved before login. Guest goes to reduced bottom tabs. Inputs/rules. Account type selection and stored onboarding flag govern route choice. Failure. Startup may proceed after initialization catches; user feedback depends on screen. Sources: lib/main.dart:128-140; lib/app/viewmodels/account_type_viewmodel.dart:11-96; lib/app/views/account_type/account_type_view.dart:16-130.

Acceptance check: Fresh install shows onboarding; returning guest reaches four tabs; selecting each type opens its corresponding form; login remembers the selected type for role validation.

M02 Ordinary user registration

Entry and actions. Signup form proceeds through basic information and address/preferences; the controller loads castes, degrees, occupations, countries, states and cities, handles photo selection, validates fields, and submits a backend registration. A dashboard-created profile path and approval message exist. Inputs. Name, email, phone, password, gender, date of birth, photo, education/occupation/caste, address and preference selections are represented across the form/controller. Exact backend approval criteria are unverified. Failure. Validation and repository errors surface in controller UI. Sources: lib/app/views/signup/signup_view.dart:22-360; basic_info_view.dart:12-140; address_preferences_view.dart:14-110; lib/app/viewmodels/signup_viewmodel.dart:31-1194; lib/app/domain/repository/user_management_repo/user_management_repo_impl.dart:96-149.

Acceptance check: Invalid required values block progress; dependent location options load in order; completed form sends one registration request; failure remains actionable; dashboard-created users follow the distinct return path.

M03 Matrimonial registration and managed profiles

Entry and actions. Matrimonial signup uses VendorRegistrationViewModel and the vendor registration API. Role 3 dashboard displays account information and routes to add a user or view managed profiles. Managed profiles can be inspected, their images updated, and a delete action is presented. Rules. The role 3 dashboard replaces the ordinary Profile tab. Server authority for managed-profile deletion needs backend confirmation. Sources: lib/app/views/signup/matrimonial_signup_view.dart:22-607; lib/app/viewmodels/vendor_registration_viewmodel.dart:18-503; lib/app/views/dashboard/dashboard_view.dart:485-511; lib/app/viewmodels/matrimonial_profiles_viewmodel.dart:34-465; lib/app/domain/repository/user_management_repo/user_management_repo_impl.dart:985-1088.

Acceptance check: Role 3 sees Dashboard; managed profile list loads for the admin ID; add, image update and delete paths display API failures clearly.

M04 Login, session and logout

Flow. Login posts username/password/grant_type to token endpoint, stores token locally, fetches donor claims with bearer authorization, checks selected account type against role ID, saves session and creates/updates a chat user. AuthService checks stored session at startup, handles Firebase authentication, FCM token and logout cleanup. Validation. Email required and syntactically checked; password minimum length four in the login controller. Failure. Token and claims errors are shown separately; the repository sets a SharedPreferences login flag after token success before claims succeed. Sources: lib/app/viewmodels/login_viewmodel.dart:52-285; lib/app/domain/repository/user_management_repo/user_management_repo_impl.dart:60-189; lib/app/viewmodels/auth_service.dart:81-273.

Acceptance check: Invalid credentials do not navigate; role mismatch is blocked; successful role-appropriate session reaches the correct route; logout clears visible user state. Confirm partial-token failure behavior with product/backend owner.

M05 Password recovery and password change

Flow. Forgot password loads a phone number, requests Firebase phone verification, accepts or pastes an OTP, and after verification calls backend reset_password with the email and new password. Signed-in change password uses the backend update password operation. Failure. OTP and reset failures are handled in controller paths; account-to-phone mapping must be confirmed server-side. Sources: lib/app/views/forgot_password/forgot_password_controller.dart:100-489; lib/app/views/profile/change_password/change_password_controller.dart:28-79; lib/app/core/services/network_services/end_points.dart:52-60.

Acceptance check: OTP request/verification and resend states are visible; invalid OTP cannot advance; password reset and signed-in change display success/failure consistently.

User details fetches profile information, checks connects and chat relationship, and offers media previews and communication actions. Guest action gates are present in controller logic. Failure. Loading/error UI is controller-dependent; backend profile visibility and gender policy need confirmation. 8. Open questions and gaps

  1. Backend claims after token: The client calls GetDonorClaims after a successful token and treats a 500 as error. Backend logs/schema are required to explain failures; do not define this as expected behavior. login_viewmodel.dart:111-155; user_management_repo_impl.dart:152-189.
  2. Connects atomicity: Confirm exact debit trigger, refund/retry behavior, recipient key and server transaction/idempotency contract across backend and Firestore. firebase_service.dart:777-895; system_config_repo_impl.dart:307-334.
  3. Purchase fulfillment: In-memory duplicate guards do not survive process death; confirm server receipt validation, unique transaction IDs and restore handling. buy_connects_controller.dart:228-456.
  4. Approval and roles: Define who approves ordinary and matrimonial accounts, status lifecycle, and backend authorization for role 3 management. Client labels alone do not establish server permissions. signup_viewmodel.dart:1014-1090; login_viewmodel.dart:162-193; matrimonial_profiles_viewmodel.dart:300-323.
  5. Client secrets: EnvConfig reads service-account fields and an asset JSON path. Confirm no service-account private key is shipped to the app and rotate any exposed credential. env_config_service.dart:26-27,73-121; pubspec.yaml:187-204.
  6. Account deletion: Confirm backend data retention, chat partner visibility and consistency of Firestore cleanup. profile_viewmodel.dart:372-502; profile_view.dart:639-739.
  7. Delivery semantics: Callable function may return success after an internal error; define whether that is acceptable and how undelivered messages are repaired. functions/index.js:6-215.
  8. Platform/build: Confirm iOS notification entitlements/provisioning, Android overlay permission need, release signing, and actual store product configuration. ios/Runner/Runner.entitlements; android/app/src/main/AndroidManifest.xml; buy_connects_controller.dart.
  9. Documentation-only assertions: Existing Markdown fix/test notes are B until checked against compiled behavior. The account-deactivated route has no active GetPage registration. lib/app/core/routes/app_pages.dart:215-223; root Markdown notes.
